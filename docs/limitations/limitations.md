# Limitations

What the prototype does not do. "Seen as" is what the traveller or a reviewer
would notice. State as of 2026-10-06; code under
`halcy_case_material/starter/agent/`.

## Payment hand-off

| #   | Limitation | Seen as | What would lift it |
| --- | ---------- | ------- | ------------------ |
| L1  | The traveller must sit at the machine that runs the browser | No remote or phone traveller | The WebView path (`agent/WEBVIEW-PLAN.md`) |
| L2  | The visible browser opens only when validation needs it, tucked as small as macOS allows (500x375) in the far corner of the screen and minimised at once; at the hand-off it is restored to full size near the top left and brought forward. macOS keeps windows on a display, so it cannot start fully out of sight: a small corner box may show for a moment. Screenshots are refused while it is minimised (Chromium does not paint it) | A brief flash in a screen corner when validation starts; no screenshots of search or validation pages | A platform window that can start hidden, or the WebView path |
| L3  | The browser closes when the run ends, seconds after the hotel's confirmation appears | The traveller cannot re-read the hotel's confirmation page; the reference is in the chat only | Keep the window until the next chat message |
| L4  | A status needs the main tab to come back to the hotel's site and show a confirmation with a reference | Hotels that confirm in a pop-up, a new tab or only by email end as `unconfirmed` or `timed_out` | Per-pattern handling; a later re-check |
| L5  | New tabs and pop-ups are never followed, and a stray tab is not closed | A payment that finishes in a pop-up is not seen; two tabs may be visible | Tracking pages opened by the traveller without reading them |
| L6  | Errors inside the payment provider's frame are never read | Halcy cannot say why a bank code was refused; a decline is only known if the hotel's own page says so or the traveller presses "It didn't work" | Nothing, by design (trade-off T13) |
| L7  | The hold is read from a mm:ss countdown, a length in words ("for 10 minutes"), or "until HH:MM" on a line that says the room is held; otherwise from what validation read, less the time since. An expired hold is recognised only from English wording (expired, released, lapsed) | A hold the page shows as a progress bar or in another language is not understood; the wait is then 5 minutes and the traveller is told the hotel did not say how long. A time of day is trusted only if it fits the stated length, so a page in another time zone falls back to the estimate | More patterns, or a model read right before the hand-over |
| L8  | The amount check asks whether each agreed number is somewhere on the page, not next to its label | A page where "charged now" and "paid at the hotel" swapped, or the figure appears elsewhere, passes. When a figure is gone, the message names it and quotes the labelled line if there is one | Label-bound extraction checked against the page |
| L33 | The last look before the hand-over reads the open page; it does not reload it | A room taken by someone else or a price changed on the hotel's server is only found when the hotel refuses at the end, after the traveller has typed the card | Reload before the hand-over where the hotel keeps the session across a reload |
| L34 | A fresh hold is asked for once, by running the validation agent again | About a minute of waiting and one more model run; a second refusal ends the run | A cheaper code path per hotel |
| L35 | The hotel's quoted message can carry text from a link next to it | "...The payment was cancelled. Try another card" | Quote the sentence, not the line |
| L36 | A second validation of the same room compares against the price the traveller agreed to. The root cause, validation writing the payment page's total over the search price, is fixed in `agents/validation.ts`; the hand-off still adds a note to the second validation as a second guard | Nothing seen since the fix | Drop the note once repeats confirm it |
| L37 | A hold's end time ("bis 15:02 Uhr") is trusted only if it fits the stated length from the machine's own clock; a page that gives its time in the hotel's time zone falls back to validation's reading or, without one, a 5-minute wait | On a hotel abroad the traveller may get 5 minutes, told the hotel did not say how long, though the page said more | Read the hotel's time zone from its address |
| L38 | The activity log shows the steps from the run log, after its card scrub, with the traveller's name, email and phone removed; between hand-over and outcome only two fixed lines | Long runs give long logs; nothing is summarised | A summary line per agent |
| L9  | A retry after a decline reloads the payment address | On a hotel where a reload loses the session the retry fails | Use the page's own "try again" control |
| L10 | `unconfirmed` and `session_lost` have no automatic follow-up | The traveller is asked whether the hotel's email arrived; nothing checks again later | A re-check, reopening the page, email matching with permission |
| L11 | Only card numbers are scrubbed from chat messages | A bank code typed into the chat reaches the history and the model | Withhold short all-digit messages during the hand-off |
| L12 | The hand-off card's buttons stay pressable after the wait has ended | Pressing them does nothing | A way for the chat to retire a card |
| L13 | Card and bank-code fields are recognised by their attributes first (`autocomplete` cc-* and one-time-code, `type=password`, a `name` or `id` such as card, cvc, exp, otp), then by label in English, German, French, Spanish, Portuguese, Italian, Swedish and Dutch, then by a Luhn-valid value. A field marked by attributes is never read in the page at all; one found only by its label is read into the process and emptied before anything else sees it | A field with neither attributes nor a label in those languages is read until it holds a full card number. Checked on a German hotel (third mock): all four card fields withheld | More languages; treat every field on a page with a foreign payment form as sensitive |
| L14 | Screenshots mask embedded frames only, and are refused while the visible window is minimised | Card fields placed directly on a hotel's page would be visible in a screenshot taken after the hand-off; none is taken there today | Mask sensitive fields in screenshots too |
| L15 | The Playwright process could read every frame; it is code, tests and the run-log audit that stop it | The boundary is "does not", not "cannot" | The WebView or system-tab paths |
| L16 | No test that trace, HAR or video recording is off | A future change could enable one unnoticed | A test on `openBrowser` (`DESIGN.md` P5) |
| L17 | Terms and pay buttons are kept from the agent by the validation prompt, not by code | A model error could tick the conditions | Refuse actions on a detected payment page in the driver |
| L18 | A frame that navigates off the hotel's site between the check and the read has code run in it once; the result is dropped | Nothing visible | Accept, or pause frame navigation during a read |

## Agents

| #   | Limitation | Seen as | What would lift it |
| --- | ---------- | ------- | ------------------ |
| L19 | Run on two mock hotels and rehearsed on a third built blind (German, card fields on its own page); never on a real hotel site | Behaviour on a real site is unknown; the debrief runs one | Real sites, read-only |
| L20 | 85 to 176 seconds from the message to the approval card on the three example asks (search on Sonnet 5.5, the rest on Opus 5.5) | A long wait in a chat; the hotel's hold is 15 minutes | Cheaper or faster model for search; fewer turns |
| L21 | A message sent while the agent is working is only read when the agent next asks | The traveller cannot interrupt or correct a search in progress | A shared message queue (`docs/concerns.md` C2) |
| L22 | One visible browser, one candidate validated at a time; validating a second abandons the first hold. Search runs in parallel headless browsers, up to three hotels at once | Comparing two rooms at the payment-page price is slow | Parallel validation where a hotel allows two holds |
| L23 | Validation staying on the payment page is asked for in the prompt | If it wanders, the hold runs down; the hand-off's checks catch a changed page | Enforce in code |
| L24 | Every hotel in `hotels.json` that answers is allowed for reading, not only the one being booked. A hotel that does not answer within 1 s at the start of a run is left out for the whole run | A hotel that is slow to start is not offered in that run | Re-probe before each search |
| L25 | One conversation, one traveller, one run at a time | No group chat, no two bookings at once | Sessions in the chat server |
| L26 | The traveller's name, email and phone are sent to the model provider and written to the run log | Nothing in the mock; a policy question in production | Minimise and document |
| L30 | An estimate in the traveller's currency is the ECB reference rate, not the bank's | The traveller sees "≈ 7,890 kr (estimate at the ECB rate of 5 Oct ...)" beside the hotel's figure; their bank's rate, card fees, and the rate on the day the part paid at the hotel is charged can all differ. A comparison or a limit within 3% is called too close and asked | The traveller's own card's rate and fees, which no public source gives |
| L31 | Currencies are recognised from a short list of symbols, codes and words; "$" and "kr" each stand for several currencies and are treated as compatible with all of them | A room list in "$" and a payment page in CAD are not flagged as different | Read the currency code from the page's markup where it exists |
| L32 | An offer to "pay in your own currency" made inside the payment provider's frame is never seen | Halcy cannot warn about the provider's own exchange rate; the hand-off card only says what the bank should show | Nothing, by design (trade-off T13) |
| L37 | That a room price has changed is noticed by the validation model, which reports the room line as `price_room`; code compares that figure only once the traveller has accepted a new price. A second change after an acceptance is asked about again by rule, but the mock raises its price once, so that has only been unit-tested | A validation that misreads the room line could accept a changed price unasked. The hand-off's check that the agreed amounts are on the page is the backstop | Compare the found price with the reported room line in code for every validation, once it is settled how sites that list per-night prices are recorded |
| L38 | A charge the room list states is only counted at search when the search model records it in `fees_known`; charges that first appear later are counted only after validation | A room can rank as fitting the limit and then be over it on the payment page; the traveller is then asked, never booked silently | Read stated charges per hotel layout in code |
| L39 | The price check reads the page text the search agent was shown; a price drawn only as an image, or split over elements in a way the text does not keep together, is refused as "not on the page" | A hotel with image prices cannot be recorded; the agent says it could not read a price | Read amounts from the page's markup as well |
| L40 | Guide figures are recognised by words next to them ("about", "approx.", "as a guide", "≈") or a sentence naming the guide currency, in English | A guide marked only by styling, or in another language, is taken as a price unless the page states which currency it charges in; then code still refuses it | More languages; ask the page's markup |
| L41 | Scoring ranks `price_total` as written across currencies: 594 GBP counts as cheaper than €658.24 | A hotel pricing in a stronger currency can rank first by score while being dearer; in case 28 Villa Aurora scored 1.0 and Casa Halcy 0.58 though Casa Halcy was ≈7,407 kr against ≈7,890 kr. The orchestrator's `compare_prices` converts and corrects the choice, and the test-mode trace says when scores compare different currencies | Convert prices to one currency in `scoreAll` with the ECB rates it already loads |
